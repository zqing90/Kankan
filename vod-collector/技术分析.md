# 视频采集站技术同构性分析 & 配置化接入方案

> 实测样本：32 个资源站（23 个存活），测试片《空枪》，2026-11-06

## 一、结论

**技术栈完全相同，是同一个 CMS 的不同白标部署。** 它们不是"类似的产品"，而是"同一个产品的不同域名"。

- 协议：全部基于 **苹果CMS（maccms V10）** 的 `provide/vod` 接口规范，请求参数、返回结构、播放地址拼接规则一字不差。
- 差异只在 4 个可枚举的运维层面：接口路径变体、播放地址形态、搜索是否开放、域名是否还活着。
- 所以**公共部分可以抽到 90% 以上**：一套 `protocol + normalize` 核心，站点差异全部塞进配置或解析器分支。落到代码上，23 个站的接入成本 = 1 个适配器 + 23 段 JSON。

反例也说清楚：**"配置化"的边界在协议层，不在解析层**。协议（参数、字段、拼接规则）可以 100% 配置化；播放地址形态必须靠代码判断（4 种形态靠特征自动识别，无需配置）。把解析也硬塞进配置，会得到一堆正则字符串，反而更难维护。

## 二、同构性证据

### 1. 响应格式：23/23 默认 JSON

文档里写的是 XML 接口（`at/xml`），但实测**所有站默认就返回 JSON**，`at=json` 全站支持。这是最容易踩的坑——按文档写 XML 解析器等于白写。

### 2. 详情字段：82 个公共字段，差异 3 个

对 23 站同一部片取详情，字段集合取交集：

| 指标 | 结果 |
|---|---|
| 单站字段数 | 83 ~ 85 |
| 公共字段 | **82** |
| 差异字段 | `vod_pic_original`、`vod_pic_screenshot`、`vod_pic_thumb_original`（都只是扩展图片） |

也就是说：片名、年份、地区、语言、演员、导演、简介、分类、更新时间、播放源、播放地址——**关键字段 0 差异**。

### 3. 播放地址拼接：一套规则通吃

```
vod_play_from = "liangzi$$$lzm3u8"                 // $$$ 分隔多个播放源
vod_play_url  = "HD$https://.../index.m3u8#TC$https://..."  // # 分隔集数，$ 分隔「集名/地址」
```

多集剧就是 `第01集$url#第02集$url#...`。这套规则 23 站无一例外，`parsePlayUrl()` 一个函数就吃下了。

### 4. 参数集完全一致

| 用途 | 参数 |
|---|---|
| 分页列表 | `?ac=list&pg=1&t=分类&h=最近N小时&pagesize=20` |
| 搜索 | `?ac=detail&wd=关键词` |
| 详情 | `?ac=detail&ids=1,2,3` |
| 格式 | `&at=json` |

## 三、真实差异（4 类，全部可收敛）

| # | 差异 | 分布 | 处理方式 |
|---|---|---|---|
| 1 | 接口路径变体 | `/api.php/provide/vod/`（21）、`/xinlangapi.php/provide/vod/`（新浪）、`/provide/vod/`（金鹰） | `stations[].path` |
| 2 | 播放地址形态 | 直接媒体流 / 多级 master / 分享页 HTML / AES-128 | `src/hls.js` 按特征自动识别，**不需要配置** |
| 3 | 搜索开放度 | 16 站开 `wd`；7 站返回「暂不支持搜索」 | `stations[].search = "wd" \| "none"`，关闭的走 `ac=list` 全量增量 |
| 4 | 域名漂移 | 本次 9/32 已失效；存活站也常换域名 | `stations[].hosts` 数组 + 失败自动切换 |

### 播放地址的 4 种形态（这是唯一必须写代码的地方）

| 形态 | 代表站 | 特征 | 解析要点 |
|---|---|---|---|
| `media` | 暴风 | 直接是 `.ts` 列表，相对路径 | 按 baseURL 补全 |
| `master` | 牛牛、最大 | `#EXT-X-STREAM-INF` + 子列表，最多 2 级 | 递归 + 选最高 `RESOLUTION` |
| `share-page` | 量子、非凡 | 返回的是 HTML 播放页 | 正则抠出 `/2026.../index.m3u8?sign=xxx` 再递归 |
| `AES-128` | 光速、红牛、极速、新浪、金鹰、魔都、飘零、虎牙、360 | 带 `#EXT-X-KEY:METHOD=AES-128,URI="enc.key"` | 不用解密即可验证取流；前端 hls.js 自动带 key 请求 |

## 四、一个额外发现：14 家站，其实没那么多片源

《空枪》在 14 个站共 46 条播放线路，但：

- 只有 **40 条互不相同的片源路径**；
- 6 个站（光速/红牛/极速/新浪/金鹰/虎牙）的线路**段数、时长、首片体积完全一致**（2778 段 / 2h40m / 701KB），是同一份转码产物的不同域名镜像；
- 最大资源的 HD 地址与牛牛 HD 地址 **path 完全相同**（`/yyv14/202610/23/jhuXiwi0bP27/`），只是 CDN 域名不同。

**含义**：多站并发采集的收益不在"更多片源"，而在**可用性冗余**（谁先挂谁后挂）和**更新速度**（谁先出片）。选源策略应当按「清晰度 + 可播性 + 时长完整度」打分，而不是盲目相信站的数量。

实测也确实抓到了这个问题：最大资源给的是 128 分钟版本，其余站是 161 分钟完整版——同一部片，不同站给的是不同剪辑。所以聚合层加了 `shortVersion` 标记（正片时长 < 8000 秒且非解说/预告，判为枪版/删减）。

## 五、架构：三层适配 + 配置驱动

```
                 ┌──────────────────────────────────────┐
                 │  config/stations.json（唯一差异来源） │
                 │  hosts / path / search / priority     │
                 └───────────────┬──────────────────────┘
                                 │
   ┌─────────────────────────────▼──────────────────────────────┐
   │ 协议层  src/maccms.js                                       │
   │   list() / search() / detail() / classes()                  │
   │   parsePlayUrl()  $$$ 线路 / # 集数 / $ 名称+地址            │
   │   normalizeVod()  85 字段 → 18 个统一字段                    │
   └─────────────────────────────┬──────────────────────────────┘
                                 │
   ┌─────────────────────────────▼──────────────────────────────┐
   │ 解析层  src/hls.js                                          │
   │   resolvePlay() 自动识别 media / master / share-page / AES  │
   │   → { 清晰度, 时长, 段数, 是否加密, 首片能否取到 }            │
   └─────────────────────────────┬──────────────────────────────┘
                                 │
   ┌─────────────────────────────▼──────────────────────────────┐
   │ 编排层  src/collector.js                                    │
   │   多站并发 → 按「片名+年份」聚合 → 同站同地址去重            │
   │   → 评分排序（可播 > 清晰度 > 时长完整）→ 输出统一模型       │
   └─────────────────────────────┬──────────────────────────────┘
                                 │
              ┌──────────────────┴──────────────────┐
         src/cli.js（命令行）              src/server.js（HTTP API）
```

传输层 `src/http.js` 负责三个所有站都需要的脏活：超时、重试、**多域名故障切换**、按域名限速。这层与站点无关，是所有站共享的公共设施。

### 统一后的数据模型

```jsonc
{
  "name": "空枪", "year": 2026, "type": "剧情片",
  "sources": [ { "station": "bfzy", "vodId": 169057 }, ... ],   // 谁收录了
  "lines": [                                                    // 平铺所有站的播放源
    {
      "station": "zuida", "flag": "zuidam3u8", "url": "https://.../index.m3u8",
      "playable": true, "resolution": "1920x800", "durationSec": 9649,
      "segments": 4825, "encrypted": false, "kind": "master"
    }
  ],
  "best": { ... },          // 打分最高的一条
  "shortVersion": false     // 是否疑似枪版/删减
}
```

到这里，前端/业务代码只认这一个模型，**完全不需要知道数据来自哪个站**。这也是"配置化接入"真正的价值：不是少写几行 if，而是让站点变成可随时增删的数据。

## 七、接入建议

1. **先接 3 个站跑通链路**：暴风（地址最干净，直接 m3u8 无加密）→ 量子（片库 16 万，但地址在分享页里，能验证 share-page 分支）→ 光速（AES，验证加密链路）。这三个覆盖了全部 4 种形态中的 3 种。
2. **搜索关闭的站不要放弃**：它们能通过 `ac=list&h=24` 做增量，片库一样能进；只是不能按名字找。
3. **健康检查挂定时任务**：`node src/cli.js health --json` 每小时跑一次，把 `ok=false` 的站自动禁用、把新域名写回 `hosts`。
4. **别把播放地址硬编码进库**：CDN 域名几天一换，入库只存 `station + vod_id`，播放时实时换地址。
5. **合规**：这批站给的是未授权片源，做技术验证可以，对外提供播放有侵权风险。
